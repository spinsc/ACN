## Como falar

**Sempre em português do Brasil**, inclusive comentários de código, mensagens de
commit e textos de tela. Sem jargão de programador nas explicações: quem lê decide
pelo processo da fábrica, não pelo código.

---

## Regras que não se quebram

1. **`npx vite build` antes de qualquer commit.** O `tsc` já deixou passar erro de
   sintaxe que só o build pegou. Build vermelho não vira commit.
2. **Nunca dar `git push` sem aprovação explícita do usuário.** Commitar local pode;
   publicar é decisão dele, pedida a cada vez.
3. **Na dúvida, perguntar antes de agir.** Se o pedido não está 100% claro, pergunte
   em vez de supor — vale mais uma pergunta que um retrabalho.
4. **Não alterar dado real sem pedido explícito.** Nada de "aproveitei e arrumei".
   Correção em massa só com autorização, e sempre relatando quantas linhas mudaram.
5. **Nunca apagar dado do usuário.** Para remover coluna ou tabela, confirmar antes.
6. **Teste em produção só com dado sintético.** O banco é o de produção: use registros
   `ZZTESTE`, apague depois e confira a contagem. Melhor ainda, e o padrão aqui: rodar
   com as **gravações bloqueadas** (ver Testes) e simular só as respostas de leitura.

## Ambiente

```bash
npm install                 # uma vez
npm run dev                 # dev server (use preview_start com o nome "acn-dev")
npx vite build              # gate obrigatório antes de commitar
npm run typecheck           # tsc, complementar — não substitui o build
```

O app roda em `http://localhost:5199/ACN/` (a base `/ACN/` vem do `vite.config.ts`).
O dev server é declarado em `.claude/launch.json` como **acn-dev**.

**Deploy:** `git push` para `main` dispara o GitHub Actions (`.github/workflows/deploy.yml`)
e publica no GitHub Pages. Não precisa rodar `publicar.bat` — ele é o caminho manual antigo.
Depois do push, acompanhe com `gh run watch <id>` e só considere entregue quando o deploy
terminar com sucesso.

## Banco (Supabase)

Projeto `qgemelnuqdilnggxmrdw`, organização **ACN SINAL VERDE**. URL e chave anon ficam
**hardcoded** em `src/supabaseClient.ts` — não usar `.env`.

- Autenticação é pela tabela própria `auth_usuarios`, **não** pelo Supabase Auth.
- **Desde 22/10/2026 (Etapa 17, onda 2) o banco não aceita a chave pública** (a do navegador): só quem entrou
  (crachá = sessão do banco, ver `SessaoBanco.ts`) lê e grava; a única exceção são os dois portais do cliente
  (`public/portal.html` e `veiculo.html`), que usam 4 tabelas (`configuracoes_sistema`, `veiculos_nfc`,
  `servicos_executados_nfc`, `chamados_suporte`). **Tabela nova:** ligar RLS (o trigger `ensure_rls` já liga) e criar
  a política `create policy etapa17_logado on public.<tabela> for all to authenticated using (public.esta_logado()) with check (public.esta_logado())`
  — sem política ninguém lê. **Nunca** dar direito à chave pública (`anon`) nem política "libera tudo": o padrão do banco
  já não dá. **Função nova:** quem entrou executa; a chave pública não. Dado sensível (RH, WhatsApp, e-mail, cópia de segurança)
  já nasce com regra por perfil, como em `supabase/sql/etapa17_onda1a.sql`. O que a Etapa 17 ainda não fez (separar por aba) está no plano.
- Colunas `*_norm` guardam o texto sem acento para busca (ver `SearchUtils`).
- Toda migração é feita por `apply_migration`, com comentário explicando o porquê.

## Como escrever o código

- Todo componente começa com `// @ts-nocheck` — não remover.
- **Alerta é vermelho** (pedido do usuário em 27/10/2026): todo alerta novo — janela que interrompe, faixa, selo ou aviso que a pessoa precisa ver — usa o vermelho do design system (`--acn-bad` e `--acn-bad-soft`, ou a variante/tom de erro do `Botao`, do `Selo` e da `Faixa`), para chamar a atenção; verde só para "deu certo" sem pedir ação, âmbar só para atenção leve. Não reescrever os alertas que já existem sem pedido: vale para o que nasce daqui em diante (o aviso de pendência sanada do Almoxarifado já nasceu vermelho).
- **Comentário explica o porquê, não o quê.** O padrão do projeto é registrar a decisão
  e a data ("regra definida com o usuário em 21/09/2026: ..."), para quem ler daqui a
  seis meses entender a razão.
- Edições grandes: script Python no scratchpad, com `assert` de ocorrência única e
  escrita com `newline=''` + `os.replace`. **Heredoc de bash corrompe `\n` e `\u`** —
  não use para gerar código.
- **Texto longo dentro de botão (`Botao`) vaza do cartão se a regra for `html body .classe`:** o `index.css` tem uma regra genérica de botão (`button:not([style*=...])` repetido quatro vezes) que impõe `white-space: nowrap` e pesa mais. Para o texto quebrar, use `html body .acn-b.classe:not(#acn) { white-space: normal; overflow-wrap: anywhere; max-width: 100%; }` (o `:not(#acn)` empata o peso; foi assim que o link de vínculo do Kanban do Compras foi corrigido em 26/10/2026) e confira no navegador medindo o que passa da borda do cartão.
- Antes de criar algo novo, procure o utilitário que já existe:

## Regras de negócio que já foram decididas

- **Preço:** uma conta só no sistema inteiro —
  `preço = custo (com IPI e ST) × (1 + markup) ÷ (1 − DIFAL)`. Imposto e custo fixo
  descontam da margem, não entram no preço.
- **Markup, custo e DIFAL são da formação de preços**, livres por proposta (global ou
  item a item). Cadastro de Itens é só sugestão de partida. DIFAL começa zerado.
- **Numeração de OP:** `A` (ACN) ou `D` (Detech) + PV + ano + mês. Número repetido é
  bloqueado.
- **Kit 100%** não fecha com demanda de Serralheria, Chicotes ou Compras em aberto —
  o caminho nesse caso é "liberar com pendência". A **Produção não conclui** enquanto
  a pendência não fechar, e cada pendência fecha em três etapas: setor conclui →
  Almoxarifado confirma o recebimento → PCP libera. **Exceção (decidida em 27/10/2026, OP D0793):** na pendência de **compra**, a OC com status "Recebido" já vale como recebida pelo Almoxarifado (quem confere e dá a entrada é ele): a etapa do meio vem cumprida sozinha (`compraJaRecebida`, em `OpPendencias.tsx`) e só falta o PCP liberar; Serralheria e Chicotes continuam pedindo o "Recebi".
- **Fabricação interna é sugestão, não pedido:** ao liberar o kiting o PCP vê o que é
  fabricado aqui dentro e marca o que quer solicitar. Nada vem marcado.
- **Compras é uma tela só:** toda demanda de compra vira requisição no quadro, com
  cotação e aprovação. Diferença é só o selo "Demanda de OP" ou "Demanda geral".
- **Solicitação de compra: fornecedor sugerido e link são POR ITEM** (decidido em 20/10/2026; saiu o fornecedor e o link gerais da lista toda, `itens[].fornecedor_sugerido` e `itens[].link_url`). Tudo que a pessoa preenche na solicitação aparece para o comprador (`QuadroDaSolicitacao`, em `ComprasFluxo.tsx`, na Mesa de Cotações e no Resumo).
- **Coleta pelo Compras** (decidido em 20/10/2026): ao efetivar a compra o Compras escolhe *o fornecedor envia* ou *coleta pelo Compras* (`pcp_pedidos_compra.forma_recebimento`); na coleta a data combinada (`data_prevista_recebimento`) é o dia da coleta. Coleta marcada e não feita **não entra no recebimento da Logística**; o comprador registra a coleta (`coletado_em`, lista **Coletas** por dia no Compras) e só então a compra aparece na Logística, onde o Almoxarifado confere a quantidade e a **entrada no estoque continua automática**. Coleta atrasada gera o mesmo alerta da entrega atrasada.
- **Número do pedido de compra legível e divisão do pedido sem cotação** (pedido do usuário em 30/10/2026, a partir do pedido PC-QTL54M, em que um item sem cotação segurava os outros): **o número do pedido agora é sequencial, PC-00001, PC-00002…**, dado pelo banco ao criar (gatilho `pedido_compra_numerar`, sequência `pedido_compra_seq`: qualquer tela que crie pedido, inclusive os formatos PC-DA-… e PC-ALX-…, já sai no padrão). Os 162 pedidos que existiam foram renumerados na ordem de criação, e **o código antigo fica em `codigo_antigo`** (a busca do Recebidos e o título do Resumo mostram "antes PC-XXXXX"); a **OC (OC-AAAA-NNNN) não mudou**. **Aprovar e separar o resto:** quando uma lista tem itens que nenhuma cotação cobre e a escolha de agora completa todos os que têm cotação, a janela da senha oferece, além do "Confirmar" (o pedido inteiro espera, como sempre foi), o botão **"Aprovar e separar o resto"**, com pergunta antes: os itens sem cotação saem do pedido para um **pedido novo com o mesmo número + letra (PC-00123-B), em "Pendente"**, com o mesmo solicitante, vínculo, centro de custo, comprador, prazo e anexos, e o original segue o fluxo normal (alçada e aprovação) só com o que tem cotação. A separação é a função do banco `compras_dividir_pedido` (tudo ou nada, com o pedido travado), que **renumera juntas as posições dos itens, as cotações e as vencedoras** (a escolha aponta para a posição do item) e devolve o mapa; grava o histórico "Itens separados" nos dois pedidos e o aviso na caixa de Menções de quem solicitou. Só vale na coluna **Aguardando Aprovação** (ajuste do usuário em 30/10/2026, a partir do PC-00141) e só para item que **nenhuma** cotação cobre. Se a aprovação do original falhar depois da separação, a tela diz que os itens já foram separados e que é só aprovar de novo. Já separado não se junta de volta. SQL em `supabase/sql/compras_numeracao_legivel_do_pedido.sql` e `compras_dividir_pedido_itens_sem_cotacao.sql`.
- **Só existe UM item "Conjunto Elétrico": o gatilho da estrutura de instalação** (código 1687, `eh_conjunto_instalacao`). Decidido em 21/10/2026: os outros 436 itens de nome parecido (um por OP, "CONJUNTO ELETRICO OPL Axxxx", e três de mesmo nome) foram apagados porque estavam sendo usados no lugar do gatilho nas vendas; a cópia deles está em `cadastro_itens_conjunto_eletrico_apagados_20261021`. Item novo com esse nome não deve ser criado. **A venda é reconhecida pelo vínculo com o item, mas linha sem vínculo (digitada à mão ou vinda da formação sem o item_id) é procurada pelo NOME exato** (`completarItensPeloNome`, em `ConfigEstrutura.ts`: um só item ativo com aquele nome; dois com o mesmo nome não se chuta) — caso da OP A1741.2610, de 27/10/2026, em que o Conjunto Elétrico estava escrito e a estrutura dizia que a venda não o levava.
- **Linha vendida "Sem estrutura"** (pedido do usuário em 29/10/2026, Fiat Pulse, OPL 799: 3 Interled2 vermelhos, 2 com a estrutura do conjunto elétrico e 1 fixado com ventosa): **quem decide é o PCP, na hora de montar a BOM, e não o vendedor** (correção do usuário no mesmo dia): na janela **Configurar OP** (`ConfigurarOp.tsx`), a lista "Vendido" mostra uma linha por item com a caixa "Sem estrutura" (`itens_vendidos[].sem_estrutura = true`, gravada na venda de cada OP do lote que tem a mesma linha na mesma posição, com auditoria; o painel de conferência recalcula na hora e mostra "sai/entra" para o PCP confirmar na BOM); a lista de Itens vendidos da Nova OP **não** tem a caixa. A linha continua com o **mesmo código** (225, para o estoque ficar certo no futuro), mas **a estrutura de instalação a ignora**: não recebe material, não entra na quantidade multiplicada, não gera pergunta e não aparece no aviso "nunca foram adaptados neste carro". Continua na venda e na lista sugerida da BOM. A venda pode ter duas linhas do mesmo item (uma normal, outra marcada). **Quirk que já existia:** duas linhas NORMAIS do mesmo item na venda não somam, vale a **última** (`qtdPorItem`); por isso o Interled2 da ventosa precisa da marca, não de uma segunda linha comum. Filtro em `CalculoDaEstrutura.ts` (`lerBaseDaEstrutura`), `PerguntasDaVenda.tsx` e `RespostasEmLote.tsx`.
- **BOM em pai e filho** (pedido do usuário em 29/10/2026): o material que a estrutura de instalação calcula **instala um item**, e a BOM mostra isso em árvore: o item pai e, logo abaixo e recuado, o que o instala (o parafuso, o suporte e o chicote da sirene são filhos da SIRENE). Cada linha calculada guarda `pai_item_id` e `pai_nome` na `bom_itens` (a lista continua **plana** no banco: todo consumidor segue lendo igual, e a estrutura/estoque já somavam linhas repetidas). **Quem é o pai:** o item vendido a que o material pertence; na **regra do veículo** é o **item da condição** (interligação da sirene sob a sirene, chicote da tomada sob a Tomada 12V) e, quando a regra só depende de respostas ou quantidades (chicote principal, derivação) ou o item da condição é o próprio Conjunto Elétrico, é o **Conjunto Elétrico**, que aparece só como **título** (ele não é separado: não há "conjunto elétrico" na prateleira). O mesmo material sob pais diferentes são **linhas diferentes** (o parafuso 305 do Interled2 e o do amplificador), cada uma com a quantidade do seu pai. **Onde aparece em árvore:** o editor da BOM (Configurar OP e Liberar BOM da Engenharia), a conferência/separação do Almoxarifado e a lista de separação impressa; o painel de conferência diz "instala X". **BOM antiga ou linha digitada à mão (sem pai) fica solta**, como sempre foi, e nenhuma BOM já gravada foi mexida; a diferença "sai/entra" quando uma resposta muda é por pai (e, em BOM antiga, cai na linha do mesmo item). Regras em `BomEmArvore.ts` (`agruparEmArvore`, `linhasEmOrdemDeArvore`), `ConfigEstrutura.ts` (`montarMaterial` soma por pai; `avaliarRegras` com `conjuntoId`) e `CalculoDaEstrutura.ts` (`paisDaVenda`).
- **Rádio em envio é do Telecom** (decidido em 22/10/2026): OP do tipo **Rádio** com fluxo de **envio de material** é separada, serializada e embalada pelo **Telecom**, que abre o pedido de frete para a Logística — o mesmo processo do Almoxarifado, **sem estoque por enquanto** (nada dá baixa nem é reservado). Na **venda composta** (rádio + material de adaptação na mesma OP) cada setor separa e embala o que é seu e o frete é **um só**, aberto quando o último setor terminar (a linha vendida diz quem a separa — `itens_vendidos[].setor`, que vem do Cadastro de itens e o vendedor troca; cada setor guarda a sua parte em `oples.envio_partes` pela função do banco `oples_gravar_parte_envio`, e o frete único leva peso e volumes somados e as duas caixas descritas; se um setor devolver a OP ao PCP, a parte já embalada do outro fica guardada; feito em 22/10/2026, ver `PLANOS CONCLUIDOS/PLANO_TELECOM_ENVIO.md`).
- **Serial por item da separação** (pedido do usuário em 23/10/2026): no Almoxarifado/Telecom a conferência de separação (Kiting e embalagem de envio que NÃO é "Venda para Envio") tem um campo de serial em CADA item, no lugar da caixa única com os seriais de todos; item com mais de uma unidade leva os seriais separados por vírgula. O serial fica na conferência (`oples.kit_conferencia.linhas[].seriais`, então "salvar separação" não perde) e `seriais_equipamentos` (e-mail ao Fiscal, dossiê e telas antigas leem esse texto) é montado dele. Sobrou uma caixa pequena de "outros seriais" (de algo fora da lista; `kit_conferencia.seriais_outros`) que também guarda, inteiro, o texto antigo das OPs de uma caixa só. Regra mantida: o kit só fecha com pelo menos um serial (em algum item ou nos "outros"); serial por item é opcional. A "Venda para Envio" continua com serial por produto (linhas produto + serial).
- **Serial na Venda para Envio vem em lista pronta** (pedido do usuário em 27/10/2026): a embalagem e o kiting em lote da Venda para Envio **não pedem mais o produto à mão**. A lista nasce das linhas vendidas, só com os itens que têm a marca **"Tem número de série" do Cadastro de itens** (`cadastro_itens.tem_serial`, começa desligada em todos; o Conjunto Elétrico nunca tem, mesmo marcado; frete e serviço também não), **uma linha por unidade vendida**, com o produto escrito e travado; o Almoxarifado digita só o serial, e **cada linha da lista exige o seu serial** (na venda composta, a parte do Almoxarifado continua opcional). Remessa parcial: a lista acompanha as unidades da remessa (parte proporcional) e desconta o que já foi serializado. **Venda sem nenhum item marcado, ou com serial já gravado antes (kiting em lote), segue com a digitação à mão de sempre.** **A marca se liga na própria tela da BOM** (pedido do usuário em 27/10/2026, para não ter que ir ao Cadastro toda vez): cada linha da BOM ligada ao cadastro tem a caixa **"Serial"** (`BomEditor`, em `OpItens.tsx`, usada na liberação da BOM da Engenharia e no Configurar OP), que grava `tem_serial` direto no item (vale para todas as OPs, fica no histórico do item, o Conjunto Elétrico fica travado); também dá para marcar no Cadastro de itens.
